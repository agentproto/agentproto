## Abstract

A **memory item** is a small typed assertion about a principal or its
work: who the user is, how they want the agent to behave, what is going
on in a project, where to find something. `memory/v1` fixes how one item
is stored: a markdown file whose YAML frontmatter carries the
[AIP-10](/docs/aip-10) base fields, a closed `type`
(`user | feedback | project | reference`), a lifecycle
(`active`, then `superseded` or `archived`), a `lifetime`, and
provenance and capture blocks; the markdown body is free. It then
specifies the **store** a host reads and writes items through, and the
**projection** that shows in-force items to a harness session at spawn
and captures the session's native-memory changes back as proposals.

## Motivation

Agents already keep this kind of memory, each in its own shape: a
harness's native auto-memory directory, a system-prompt file, a clerk's
facts store. None of them can be read by another runtime, and none
records where a claim came from or whether it still holds. A writer and a
reader that agree on one document can exchange items without a
translation per pair, and a reader can tell a live item from a retired
one.

Memory is not knowledge, and not a lesson:

- **[AIP-10](/docs/aip-10) knowledge entries** are curated wiki pages
  compiled from immutable raw sources and pulled by query. A memory item
  is mutable, scoped to a principal, and carries its own lifecycle; it is
  pushed into context at spawn and searched on demand. A memory item
  reuses the AIP-10 base fields so the same tooling can list both, but it
  is a separate doctype.
- **[AIP-11](/docs/aip-11) lessons** are transferable heuristics
  distilled from completed runs, with trigger conditions and success
  counts. A memory item is a single assertion (a preference, a fact about
  a project, a pointer), not a playbook entry; it has no trigger and no
  outcome count.

## Specification

The keywords MUST / SHOULD / MAY are RFC 2119.

### 1. Document

A memory item is one UTF-8 markdown file: a YAML frontmatter block
fenced by `---` lines, then a markdown body. The frontmatter is validated
by [`MEMORY.schema.json`](https://github.com/agentproto/agentproto/tree/main/specs/resources/aip-72/draft/MEMORY.schema.json),
in which the `body` property stands for the markdown after the closing
fence. The registry file name is `MEMORY.md`; a store MAY name item files
otherwise (the reference store writes `items/<type>/<id>.md`).

```yaml
---
schema: memory/v1
slug: "cite-sources"
kind: feedback
title: "Cite sources"
updated_at: "2026-10-13T11:30:00.000Z"
id: mem_test001
name: "cite-sources"
type: feedback
polarity: do
description: "Always cite sources"
tags: ["global", "agent:assistant"]
lifetime: { kind: "durable" }
status: active
created: "2026-10-13T11:30:00.000Z"
written: "2026-10-13T11:30:00.000Z"
decidedBy:
  rule: "classifier-confident"
  source: "builtin"
provenance:
  source: "converse"
  quote: "always cite your sources"
  at: "2026-10-13T11:00:00.000Z"
  extractorVersion: "extractor@3"
capture:
  mode: "batch"
  producer: "clerk:user"
  capturedAt: "2026-10-13T11:00:00.000Z"
---

Always cite sources.
```

### 2. Fields

| Field | Type | Required | Meaning |
|---|---|---|---|
| `schema` | `"memory/v1"` | canonical | Doctype discriminator. |
| `slug` | string, `^[a-z][a-z0-9-]*[a-z0-9]$`, 2 to 96 chars | canonical | Stable kebab-case identifier (AIP-10). |
| `kind` | string, `^[a-z][a-z0-9-]*$` | canonical | AIP-10 spelling of the item type; one of `user`, `feedback`, `project`, `reference` for a `memory/v1` item. |
| `title` | string, 1 to 200 chars | canonical | Human-readable title (AIP-10). |
| `updated_at` | ISO 8601 date-time | canonical | Last content write (rule 6). |
| `id` | string | legacy | Store identifier (e.g. `mem_qc8f407g`). |
| `name` | string, up to 1000 chars | legacy | Slugified name, kept apart from `slug` for round-trip. |
| `type` | `user \| feedback \| project \| reference` | legacy | The closed memory type. |
| `description` | string, up to 4000 chars | no | One-line summary, independent of the body. |
| `tags` | string[] | no | Free labels; scope anchors in formatted form (`global`, `project:<slug>`, `agent:<slug>`, `pr:<owner>/<repo>#<n>`). |
| `polarity` | `do \| dont` | no | Feedback polarity; only on `feedback` items. |
| `lifetime` | object | no | How long the item holds (section 4). |
| `status` | `active \| superseded \| archived` | no | Lifecycle (section 3); absent means `active`. |
| `created` | ISO 8601 date-time | no | Creation time. |
| `written` | ISO 8601 date-time | no | Legacy mirror of `updated_at`. |
| `decidedBy` | `{ rule, source }` | no | The rule that decided the item, and where that rule came from. |
| `provenance` | object | no | Where the claim was observed (section 5). |
| `capture` | object | no | Who and how captured it (section 5). |
| `evidence` | object | no | Trust and impact accounting at write time (`sourceKind`, `trust`, `explicitness`, `corroborations`, `contradictsActive`, `impact`, `lifetime`, `anchorsResolved`, `ageHours`, `flags`). |

"canonical" fields are REQUIRED on a canonical `memory/v1` item. An item
without them is valid only if it carries the legacy trio `id`, `name`,
`type` (items written before this doctype existed). No other top-level
key is allowed.

### 3. Lifecycle

```
active ──> superseded
   └─────> archived
```

A writer creates an item `active`. `superseded` means a newer item
replaces it (for example, a duplicate folded into another). `archived`
means it is retired with no replacement (its lifetime ran out, or its
anchor no longer resolves). Both are terminal. An item is retired by
rewriting its `status`, not by deleting the file.

### 4. Lifetime

| `kind` | Extra field | Holds |
|---|---|---|
| `durable` | none | until retired |
| `until` | `at` (date-time), REQUIRED | until `at` |
| `while` | `anchor`, REQUIRED | as long as the anchor holds (a task open, a PR open...) |
| `session` | none | for the session that produced it |

An anchor is `{ kind: "global" }`, `{ kind: "project" \| "contact" \| "agent", slug }`,
`{ kind: "task" \| "session", id }` or `{ kind: "pr", repo, number }`.

### 5. Provenance and capture

`provenance` records where the claim was observed: `source` (a source
class such as `converse` or `transcript`), `sessionId`, `ref`
(an opaque pointer into the source, such as a message uuid or a file
path), `quote` (the verbatim text backing the claim), `at` (when it was
observed) and `extractorVersion` (which extractor generation produced
it).

`capture` records who and how captured the item, apart from where the
claim came from: `mode` (`live` during the session it describes, or
`batch` by a later pass), `producer` (the capturing component) and
`capturedAt`.

### 6. Body

The markdown body is free. It holds the assertion itself in prose; a
writer MAY render a feedback item as the rule, then a "why" and a
"how to apply" paragraph, but readers MUST NOT depend on any body
structure.

### 7. Conformance

Writer rules:

1. A writer MUST emit frontmatter that validates against
   `MEMORY.schema.json`, and MUST set the canonical fields
   (`schema`, `slug`, `kind`, `title`, `updated_at`) on every item it
   creates.
2. When both `kind` and `type` are present they MUST be equal.
3. Every string-typed field MUST be written so a YAML 1.2 parser reads a
   string: a value such as `true`, `null`, `no` or `2026` MUST be quoted.
4. An optional field with no value MUST be omitted, never written empty
   (in particular `provenance.sessionId` and `provenance.ref`).
5. `polarity` MUST NOT be set on an item whose type is not `feedback`.
6. A writer MUST set `updated_at` when it creates the item and when it
   changes any field other than `status`. A status-only rewrite MAY leave
   `updated_at` unchanged, and MUST leave every other byte of the file
   unchanged.
7. A writer MUST only move `status` from `active` (or absent) to
   `superseded` or `archived`, and MUST NOT move it out of either.
8. A writer SHOULD record `provenance.source`, `provenance.at` and, when
   the claim comes from a quotable source, `provenance.quote` verbatim.

Reader rules:

9. A reader MUST accept both canonical and legacy items (section 2), and
   MUST treat an absent `status` as `active`.
10. A reader MUST NOT present a `superseded` or `archived` item as being
    in force; it MAY show it as history.
11. A reader SHOULD treat an `active` item whose lifetime no longer holds
    (an `until` past its `at`, a `while` whose anchor is gone, a
    `session` item outside its session) as not in force, even before a
    writer archives it.
12. A reader MUST NOT reject an item because of its body.

### 8. Store

A **memory store** holds memory items and offers six operations. It
keys items by `id`: a commit of an item without one gets an `id`
assigned by the store. `slug`, when present, is a second handle (rule
14). The
files are the source of truth; any index a store keeps (full text,
embeddings, a knowledge provider) is derived from them and MUST be
rebuildable from the files alone.

- **write** an item, in one of two modes. `propose` records a
  proposal: a `memory/v1` document that is not an item yet, is not in
  force, and is never projected into a session. `commit` creates the
  item, or replaces the content of an existing one.
- **read** one item by `id`. A lookup by `slug` is a `list` with the
  `slug` filter, and finds at most one active item.
- **list** items, filtered by type, status, tag (scope anchors in
  formatted form) and whether the item is in force (rules 10 and 11).
  With `proposals: true` it lists the pending proposals instead.
- **search** items by a free query. A store MAY delegate the query to
  an [AIP-10](/docs/aip-10) knowledge provider that indexes the items;
  every hit MUST say whether it is a memory item of this store
  (`source: "memory"`, with its `id`) or something else the provider
  returned (`source: "knowledge"`).
- **supersede** an item by a new one: the new item is committed, then
  the old item's `status` becomes `superseded`. The old item stays
  readable.
- **archive** an item: its `status` becomes `archived`. The item stays
  readable.

A proposal that will not be committed is dropped with **dismiss**. A
proposal is not an item, so dropping it erases nothing that was in
force.

```ts
type MemoryType = "user" | "feedback" | "project" | "reference"
type MemoryStatus = "active" | "superseded" | "archived"

// MemoryDocument: the frontmatter fields of section 2 plus `body`.
interface MemoryRecord {
  item:        MemoryDocument
  revision:    string             // opaque; changes on every byte change
  proposalId?: string             // set on a proposal, absent on an item
}

interface MemoryFilter {
  type?:      MemoryType | readonly MemoryType[]
  status?:    MemoryStatus | readonly MemoryStatus[]
  slug?:      string              // matches at most one active item
  tags?:      readonly string[]   // match any, e.g. ["global", "project:acme"]
  inForce?:   boolean             // rules 10 and 11, at the store's clock
  proposals?: boolean             // list proposals instead of items
}

interface MemorySearchHit {
  source:   "memory" | "knowledge"
  id?:      string                // REQUIRED when source is "memory"
  slug?:    string
  title:    string
  snippet?: string
  score?:   number
  ref?:     string                // provider pointer when source is "knowledge"
}

interface MemoryStore {
  write(
    item: MemoryDocument,
    opts: { mode: "propose" | "commit"; ifRevision?: string; fromProposal?: string },
  ): Promise<MemoryRecord>
  read(id: string): Promise<MemoryRecord | null>
  list(filter?: MemoryFilter): Promise<readonly MemoryRecord[]>
  search(
    query: string,
    opts?: { filter?: MemoryFilter; limit?: number },
  ): Promise<readonly MemorySearchHit[]>
  supersede(
    oldId: string,
    next: MemoryDocument,
    opts?: { ifRevision?: string },
  ): Promise<{ old: MemoryRecord; next: MemoryRecord }>
  archive(id: string, opts?: { ifRevision?: string }): Promise<MemoryRecord>
  dismiss(proposalId: string): Promise<void>
}
```

`search` and `list` default to `inForce: true` when no `status` or
`inForce` filter is given. A failed operation rejects with a conflict
(rule 17), a validation error naming the field, or a not-found error.

#### Reference layout

The reference store is a directory. Every implementation SHOULD be able
to read it, whatever it uses internally, so a store can be exported to
it and imported from it:

```
<store root>/
  items/<type>/<id>.md           # one memory/v1 item per file; path stem = id
  proposals/<proposal-id>.md     # pending proposals, not items
```

The reference store computes `revision` as the SHA-256 of the file bytes,
and a proposal id as the SHA-256 of the rendered proposal, so the same
proposal written twice lands on the same file.

Store rules:

13. A store MUST validate every committed item against the writer rules
    (1 to 8) and MUST reject an item that breaks one, naming the field.
14. An `id` MUST identify at most one item in a store, across all
    types; a commit that changes an item's `type` moves the item and
    never leaves two files for one `id`. A `slug`, when present, MUST be
    unique among the active items of the store, and a store MUST reject
    a commit that would give two active items the same slug.
15. A store MUST only change `status` from `active` to `superseded`
    (through supersede) or to `archived` (through archive), and MUST
    reject a commit that would move an item out of `superseded` or
    `archived` (rule 7). An item replaced in substance is superseded
    under a new `id`, not rewritten in place.
16. A store MUST NOT hard delete an item. The only exception is erasure
    at the principal's request (Security Considerations), which is not
    part of this interface.
17. Writes use compare-and-set. A commit that would change an existing
    item, a supersede and an archive MUST carry the `ifRevision` the
    caller last read, and the store MUST reject the operation with a
    conflict when the current revision differs. Last writer wins was
    rejected because a clerk pass and a human edit can target the same
    item, and a silent overwrite would lose a retirement or a
    correction with no trace.
18. A write is idempotent by `id`: a commit whose item equals the
    stored one in every field but `updated_at` and `written`, body
    included, succeeds without touching the file and returns the
    current revision, with or without `ifRevision`. A propose of a
    document already pending returns the existing proposal.
19. On a commit that creates an item or changes any field other than
    `status`, the store MUST set `updated_at` (and `written`, when the
    item carries it) to the commit time. Supersede and archive are
    status-only rewrites: they MUST leave `updated_at` and every other
    byte of the file unchanged (rule 6).
20. Supersede MUST commit the new item before it retires the old one,
    so an interrupted supersede leaves both items active, never neither.
    The new item MUST have a different `id` from the old one. It MAY
    carry the old item's slug: the check of rule 14 then ignores the
    item being superseded, and until an interrupted supersede is retried
    a lookup by that slug returns the item with the later `updated_at`.
21. A store MUST NOT turn a proposal into an item on its own. A
    proposal becomes an item only through a commit by a writer the
    host's write policy allows; a commit with `fromProposal` drops that
    proposal once the item is written.
22. A search hit with `source: "memory"` MUST name an item of this
    store that is in force at the time of the call, unless the filter
    asked for other statuses. A store that delegates search MUST check
    each hit against the files (the index may be stale) and drop or
    relabel a hit that no longer matches.

This revision records no link from a superseded item to the item that
replaced it; a store MAY keep that link in its own index, and the
result of `supersede` returns both.

### 9. Projection

A **projection** is how a session sees memory. It has two halves.

- **Inject**, at spawn: the host computes a digest of the in-force items
  scoped to the session and hands it to the session, either in the
  system prompt or by writing it into the harness's native memory
  location.
- **Capture**, during or after the session: changes the session made to
  its native memory are read back and written to the store as
  proposals. A capture never commits.

Each [AIP-45](/docs/aip-45) harness adapter declares what it supports in
`capabilities.memory`:

```ts
interface MemoryProjectionCapability {
  inject:  "native-dir" | "system-prompt" | "none"
  capture: "native-dir-diff" | "none"
}
```

- `inject: native-dir` means the harness reads a native memory
  directory or file at start, and the adapter can write items into it.
- `inject: system-prompt` means the harness has no native memory but
  accepts appended system-prompt text at spawn.
- `inject: none` means neither.
- `capture: native-dir-diff` means the harness writes its native memory
  location during the session, and the adapter can diff it against what
  was projected.

An absent declaration reads as `{ inject: "none", capture: "none" }`.
Like a capability in [AIP-71](/docs/aip-71), the declaration is
metadata: it does not enable a projection by itself.

#### Resolution

Native first, system prompt as the fallback, one owner per session, as
in AIP-71 section 4:

1. When the harness declares `inject: native-dir` and the host
   implements the native projection for that adapter, the digest is
   written into the native location.
2. Otherwise, when the harness declares `native-dir` or
   `system-prompt` and the host can append to that session's system
   prompt, the digest is appended to the system prompt.
3. Otherwise the session gets no digest at spawn.

A host MUST use exactly one inject path per session: the same items
MUST NOT reach a session through both. A host MUST NOT claim the native
path for a harness whose native projection it does not implement, even
where the harness declares it. Capability read surfaces SHOULD report
the effective inject and capture paths.

#### Digest

The digest is the in-force items (rules 10 and 11) whose tags include
`global` or one of the session's anchors (its project, agent, task, PR
or session, as the host resolves them). An item with no anchor tag is
treated as `global`. For each item it carries:

- `type`, `id`, `slug` when present, and `title`;
- `polarity`, on a `feedback` item;
- `description` when present, otherwise the first paragraph of the
  body.

Items are ordered by type (`feedback`, `user`, `project`, `reference`),
then from the most specific anchor to `global` (session, task, PR,
agent, project, global), then by `updated_at`, newest first. The host
chooses a size bound for the digest and SHOULD keep it near a few
thousand characters. The host MUST cut whole items, never part of one,
and MUST end a cut digest with the number of in-force items left out
and the way to reach them (a search tool, when the host offers one).

On the system-prompt path the digest is one delimited block that
presents the items as recorded data, not as instructions. On the
native-dir path the adapter writes the digest or one file per item in
the harness's native format; the `id` MUST survive in a recoverable form
(for example the file name stem), so a capture can map a changed file
back to its item.

A session that gets no digest (step 3) still reaches memory if the host
exposes the store's read, list and search operations as tools. A host
SHOULD expose them to every session whose agent has memory enabled
([AIP-42](/docs/aip-42) `memory.enabled`).

#### Capture

With `capture: native-dir-diff`, the host records the native location
as it projected it, then diffs it at session end and MAY diff it
earlier ([AIP-37](/docs/aip-37) `compact-start` or `turn-end`). Each
difference becomes a proposal, never a commit:

| Difference | Proposal |
|---|---|
| a new entry | a new item |
| a changed projected item | the same `id` with the new content |
| a removed projected item | the same `id` with `status: archived` |

Accepting a proposal that carries `status: archived` is an archive of
that item (rule 15), not a commit.

A captured proposal carries `capture.mode: live`, a `capture.producer`
naming the projection, `provenance.source: native-memory` and the
session id in `provenance.sessionId`. Proposals are promoted into items
by a writer the host's write policy allows, such as the
[AIP-68](/docs/aip-68) secretary clerk (rule 21).

With `capture: none` nothing is read back from the harness; memory
written during the session reaches the store only through tools or a
later clerk pass over the transcript.

Projection rules:

23. A host MUST NOT project a proposal, or an item that is not in force.
24. A host MUST NOT commit a captured change; it MUST write it as a
    proposal.
25. A host MUST NOT inject the same items through more than one path in
    one session.
26. A host that cuts the digest MUST cut whole items and say how many
    it left out.

## Rationale

- **Own doctype, AIP-10 base fields.** Folding memory into AIP-10 would
  force a lifecycle and a principal scope onto a wiki that does not need
  them; reusing its five base fields keeps one listing and one slug
  convention across the memory layer.
- **Legacy fields kept.** Writers already have items on disk
  keyed by `id`/`name`/`type`; the schema accepts them so no migration is
  needed to adopt the doctype.
- **Three statuses.** The draft enum also listed the proposal states
  (`proposed`, `confirmed`, `rejected`, `expired`, `stale`). Those belong
  to the proposal ledger that precedes an item, not to a stored item.
- **No `anchors` array.** Scope anchors already travel in `tags` in
  formatted form; a second structured copy invites drift. The structured
  anchor survives where it carries meaning, in `lifetime.anchor`.
- **`capture` apart from `provenance`.** Where a claim was observed and
  which component wrote it down are different questions; a batch pass
  re-reading an old transcript has one provenance and a later capture.
- **Files as the source of truth.** Every harness and store can read a
  directory of markdown files; an index can be rebuilt from them, the
  reverse is not true. Search is delegated to whatever knowledge
  provider the host already runs instead of being specified twice.
- **Compare-and-set over last writer wins.** Two writers of one item
  (a clerk pass and a human) are expected, not rare; a revision check
  turns a lost update into a visible conflict at the cost of one re-read.
- **Proposals apart from items.** Captured and extracted claims are
  untrusted until a policy-bound writer commits them; keeping them out
  of `items/` means no reader, digest or search can mistake one for an
  item in force.
- **Native first, system prompt as fallback.** As in AIP-71, a harness
  that reads its own memory location gets items where it already looks,
  and its own writes there can be captured; every other harness still
  gets the same digest through the system prompt, and never both.
- **A host-chosen digest bound.** Context budgets differ per harness and
  per model; the spec fixes the order items are cut in (from the end
  of the section 9 order), that only whole items are cut, and that the
  cut is announced, not the number.
- **Status-only rewrites keep `updated_at`.** Retiring an item does not
  change what it says; keeping the timestamp lets a reader sort by
  content age, and lets the store rewrite one line.

## Reference Implementation

The document (sections 1 to 7) is implemented by
[`@agentproto/memory`](https://github.com/agentproto/ts/tree/main/packages/memory):
`defineMemory`, `parseMemory`, `renderMemory`, `validateMemory`, and the
lifecycle helpers `memoryStatus`, `isAllowedStatusTransition` and
`isInForce`. The store (section 8) and the projection (section 9) have no
implementation yet.

## Backwards Compatibility

Not applicable (new spec). Items written before
the canonical fields existed validate through the legacy branch
(section 2). Items written with empty `provenance.sessionId` or
`provenance.ref`, or with the `anchors` array or the
`source`/`ts`/`hash` capture of the pending draft, do not validate and
need a rewrite.

The store and the projection (sections 8 and 9) are additive. A harness
manifest without `capabilities.memory` keeps loading and reads as
`{ inject: "none", capture: "none" }`.

## Security Considerations

- **Context injection.** Memory items are read back into an agent's
  context. A writer MUST route item creation through the host's write
  policy; an item whose claim comes from untrusted input (a transcript, a
  fetched page) is attacker-controlled text. `provenance` and
  `evidence.trust` let a reader weigh it.
- **Personal data.** `user` items describe a person. A store SHOULD let
  the principal list and erase their items; erasure on request overrides
  the "retire, do not delete" rule of section 3.
- **Projected text.** The digest and the native memory location are read
  by the model as context. A host MUST present digest items as recorded
  data, MUST project only the items scoped to that session, and MUST
  NOT write the items of one principal into a native location another
  principal's sessions read.
- **Captured text.** Whatever a session writes into its native memory
  may come from untrusted input it processed; this is why a capture only
  ever proposes (rule 24).
- **Secrets.** A writer MUST NOT store a secret value in any field or in
  the body, including inside `provenance.quote`.
