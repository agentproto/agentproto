## Abstract

The MCP 2026-07-28 Tasks extension gives a long-running request a handle
(`taskId`) that a client polls, updates with input, or cancels. An
[AIP-46](/docs/aip-46) session is not a request: it is a multi-turn process
that stays `running` and idle between turns.

TURN-TASK defines the only projection that is faithful to both: **one turn of
a session is one MCP task**. The task is created by the server when
`agent_start` or `agent_prompt` starts or queues a turn, resolves through a
durable ledger to `(sessionId, turnSeq)`, ends when the turn ends, and never
changes the session's own lifecycle.

## Motivation

- A client that delegates work through the session tools (`agent_start`,
  `agent_prompt`) today either blocks on a long call or polls session state it
  must interpret itself. The Tasks extension is the standard shape for that.
- Mapping a whole session to one task breaks: the session is `running` and
  `busy: false` after every turn, so the task would never leave `working`, and
  `tasks/cancel` (an interrupt) ends a turn but leaves the session alive, so it
  could never reach `cancelled`.
- The [AIP-20](/docs/aip-20) work board and MCP tasks share a word and nothing
  else. Without an explicit statement, implementers conflate a board item with
  a protocol handle.

## Scope

- In: projection of a turn started or queued by `agent_start` (with a prompt)
  or `agent_prompt` into an MCP task on the `2026-07-28` era of the authenticated
  `/mcp` endpoint ([AIP-77](/docs/aip-77)).
- Out: the `2025-11-25` era (its experimental tasks methods are not specified
  here; `tasks/result` answers `-32601` on the modern era), tasks for other
  tools, and the transport of questions and approvals while a turn waits for
  input (reused as-is: this AIP only says how the task reflects that wait).
- This AIP does **not** replace the [AIP-20](/docs/aip-20) work board and does
  **not** change the multi-turn semantics of [AIP-46](/docs/aip-46). It adds a
  handle for one turn; the session remains the unit of lifecycle, identity and
  state.

## Design principles

1. **A task is a request handle; a turn is the request.** One turn, one task.
   A second `agent_prompt` creates a new task. No task spans turns.
2. **The server decides, the client never asks.** The client only declares the
   extension; the server chooses when a call returns a task.
3. **The session stays the source of truth.** Session state is read from the
   session descriptor plus the recorded turn outcome. The projection is
   one-directional (turn to task); a task state never drives a session except
   through `tasks/update` and `tasks/cancel`.
4. **Opaque handle.** `taskId` carries no session information and is not
   derivable from one.
5. **Durable before visible.** The task record exists before the creating
   response is sent.

## Specification

### Extension declaration and creation

A client declares support in the request metadata:
`_meta["io.modelcontextprotocol/clientCapabilities"].extensions["io.modelcontextprotocol/tasks"] = {}`.
The host advertises `extensions["io.modelcontextprotocol/tasks"]` in
`server/discover` ([AIP-77](/docs/aip-77)) when the feature is enabled.

When a `tools/call` of `agent_start` (that carries a prompt) or `agent_prompt`
starts or queues a turn, and the client declared the extension, the host MUST
answer with a `CreateTaskResult` (`resultType: "task"`). Otherwise it MUST
answer with the ordinary complete result. A client MUST NOT be able to force or
suppress task creation by any parameter. If the host cannot answer a
non-declaring client without a task, it MUST reject with `-32021` carrying
`error.data.requiredCapabilities.extensions`.

A host SHOULD return a task for both tools, because both start work that can
outlive a request. This creation policy is a host decision, but it MUST be
documented by the host and applied uniformly, not left to individual tool
implementations.

### Task identity and ledger

- `taskId` MUST be generated from at least 128 bits of randomness (the
  reference format is `task_` followed by 16 random bytes in hex). It MUST NOT
  be derived from a `sessionId`.
- The host keeps a ledger entry per task:
  `{ taskId, sessionId, turnSeq, promptQueuedAt, createdAt, ttlMs, pollIntervalMs, lastStatus, lastUpdatedAt, result? }`.
  The ledger MUST be durable (survive a host restart) and MUST be written before
  the `CreateTaskResult` is sent, so `tasks/get` resolves immediately.
- `turnSeq` is the ordinal of the turn in the session at creation time:
  `turnsCompleted + (busy ? 1 : 0) + queuePosition + 1`. A turn already running
  is neither finished nor queued.
- Ledger files MUST be readable only by the host user.

### Task object

```ts
interface Task {
  taskId: string
  status: "working" | "input_required" | "completed" | "cancelled" | "failed"
  statusMessage?: string
  createdAt: string        // ISO 8601
  lastUpdatedAt: string    // ISO 8601, monotonic per task
  ttlMs: number | null     // lifetime of the task, not a cache lifetime
  pollIntervalMs?: number
}
type CreateTaskResult = Result & Task & { resultType: "task" }

type DetailedTask =
  | (Task & { status: "working" })
  | (Task & { status: "input_required"; inputRequests: Record<string, unknown> })
  | (Task & { status: "completed"; result: Record<string, unknown> })
  | (Task & { status: "failed"; error: { code: number; message: string; data?: unknown } })
  | (Task & { status: "cancelled" })
```

`inputRequests` is a map whose keys stay stable over the life of the task.
`result` is the result the originating call would have returned, bounded: the
final assistant text and the `sessionId`, never the transcript.

### Turn-to-task state mapping

| Turn state | Task status | Detail |
|---|---|---|
| prompt accepted, turn not started (queued) | `working` | `statusMessage: "queued"`, `pollIntervalMs` set |
| turn running | `working` | `statusMessage` MAY name the phase |
| turn running and the session awaits a human answer, question, or permission | `input_required` | `inputRequests` carries the pending request |
| turn ended normally (`turnsCompleted >= turnSeq`) | `completed` | bounded `result` written to the ledger |
| turn ended with a tool reporting `isError: true` | `completed` | the tool result goes in `result`, not `error` |
| turn interrupted | `cancelled` | the session stays `running`; only the turn is cancelled |
| session killed by an operator during the turn | `cancelled` | |
| session exited or errored (non-zero) during the turn | `failed` | `error: { code: -32603, message, data: { sessionId, endedReason } }` |
| host restart while the turn was in flight | `failed` | `endedReason: "daemon-restart"`, distinct from `cancelled` |
| session ended as completed by its owner during the turn | `completed` | |

`failed` is reserved for protocol-level and abnormal-end failures. A tool
error is a `completed` task whose `result` carries the error.

### Methods

- **`tasks/get`** `{ taskId }` returns `resultType: "complete"` plus the
  `DetailedTask` for the current state. It MUST be a pure, idempotent read: it
  never carries `inputResponses` and never changes state. Once a turn ends, the
  bounded `result` is stored, so a late `tasks/get` is stable even if the
  session has started another turn. `tasks/get` is not a cacheable operation:
  it carries no `cacheScope`, and the `ttlMs` field is the task lifetime, never
  a cache hint.
- **`tasks/update`** `{ taskId, inputResponses }` answers pending input and
  returns an empty acknowledgement (`{ resultType: "complete" }`). Unknown or
  already answered keys are ignored. The answer is applied through the
  mechanism that raised the request (permission, question, or run), so the
  rules of that mechanism, including [AIP-7](/docs/aip-7) (an answer to a
  prompt is not a governance decision), still hold.
- **`tasks/cancel`** `{ taskId }` returns an empty acknowledgement and is
  **cooperative**: the host interrupts the turn as [AIP-46](/docs/aip-46)
  §Interrupt describes. The turn ends, the task becomes `cancelled`, and the
  session stays alive. The transition is not guaranteed: if the turn finishes
  first, `completed` is a valid outcome. `tasks/cancel` MUST NOT kill the
  session, and `notifications/cancelled` MUST NOT be used to cancel a task.
- `tasks/list` and `tasks/result` do not exist on this era; `tasks/result`
  answers `-32601`. Discovery of sessions stays with `session_list`.

### Transport and errors

`tasks/get`, `tasks/update` and `tasks/cancel` MUST carry
`Mcp-Method: <method>` and `Mcp-Name: <taskId>`; an inconsistent header is
`-32020`. Error mapping follows [AIP-77](/docs/aip-77): `-32021` (missing
required capability) is HTTP `400`; an unknown, expired, or not visible
`taskId` is `-32602`.

### TTL

Every task has an explicit `ttlMs`. The host sweeps expired entries at start-up
and on reads. A task whose entry expired, or whose session was collected
without a recorded result, answers `-32602`. The result MUST be written to the
ledger before the entry can be purged.

### Visibility

A `taskId` is a handle, not a credential. Only the session's owner or an
ancestor authorized to see the session (the same scoping as `session_list`)
can read, update or cancel the task. A third party who learns a `taskId` gets
`-32602`, indistinguishable from an unknown task.

## Rationale

- **Turn, not session.** A session is long-lived and multi-turn; the Tasks
  extension models one request. Projecting the turn keeps both honest.
- **Server-decided creation.** The extension lets the server choose; making it
  a client option would create two result shapes per call and a new place for
  clients to disagree. Declaring support is enough.
- **Cancel the turn, not the session.** The existing interrupt ends a turn and
  keeps context. Reusing it gives `tasks/cancel` a precise, non-destructive
  meaning.
- **Random handle plus ledger.** Session ids are short and guessable; the task
  handle must not leak or be derivable from them, and must resolve after a
  restart.
- **Distinct from AIP-20.** A work board item is a unit of planned work with
  owners, dependencies and verification. An MCP task is a transient protocol
  handle. They are unrelated and neither reads nor writes the other.

## Reference Implementation

`@agentproto/runtime` (`packages/runtime/src/mcp-modern`) implements the
projection, the ledger, the state mapping and the three methods behind the host
configuration flag `mcp.tasks`.

## Security considerations

- **Unguessable handles.** 128-bit random ids; never derived from a session id.
- **No privilege through a task.** Reading, updating or cancelling a task needs
  the same visibility as the underlying session. A known `taskId` grants
  nothing.
- **No new decision path.** `tasks/update` reuses the existing answer paths and
  cannot decide a governance approval ([AIP-7](/docs/aip-7)).
- **Bounded storage.** Ledger results are bounded text, not transcripts;
  entries expire; files are user-private.
- **Cooperative cancel only.** `tasks/cancel` cannot terminate a session.

## Conformance

A host conforms to `turn-task/v1` when:

1. A client that declared the Tasks extension receives a `CreateTaskResult` from
   `agent_start` (with a prompt) and `agent_prompt`; a client that did not
   receives the ordinary result or `-32021`.
2. The task reaches `completed` at the end of the turn while the session stays
   `running`; a second `agent_prompt` creates a second task.
3. `tasks/get` implements the state mapping above and is a pure read.
4. `tasks/cancel` ends the turn, yields `cancelled` (or `completed` on a race)
   and leaves the session alive.
5. A host restart between creation and a later `tasks/get` yields `failed` with
   `endedReason: "daemon-restart"`, and the task still resolves.
6. An inconsistent `Mcp-Name` is `-32020`; an unknown, expired or not visible
   `taskId` is `-32602`; `tasks/result` is `-32601`.
7. The [AIP-20](/docs/aip-20) work board behaves identically with the feature
   on or off.
