## Abstract

`agentregistry/v1` is a **runtime primitive** — a generic catalog that
collects N `defineX`-produced doctype handles and exposes a uniform
lookup surface so hosts can assemble per-host provider/backend/tool
catalogs without re-implementing registry plumbing per doctype family.

The primitive is type-parametric over a doctype handle (`StorageHandle`,
`SandboxHandle`, `OperatorHandle`, `ToolHandle`, …) and exposes four
operations: `register`, `get`, `list`, `lookup`. It also names a
**capability metadata namespace** (`handle.capabilities`) that hosts
populate so cross-handle queries — "every storage backend that supports
FUSE-bridging", "every sandbox that pairs with `local-daemon` storage" —
are declarative rather than hard-coded in switch statements.

This AIP defines the **rules**. The reference implementation lives in
`@agentproto/registry` and is the canonical answer for hosts that don't
need bespoke storage semantics.

## Motivation

`defineStorage` (AIP-35), `defineSandbox` (AIP-36), `defineCli`
(AIP-29), `defineOperator` (AIP-42), `defineExtension` (AIP-40) all
produce **handles** — frozen, validated objects describing one
instance of a doctype. The per-author API is solved.

What's missing is the **catalog side**: every host that consumes more
than one handle of a given family ends up writing a registry for it,
each with its own:

1. Storage shape (Map keyed by `id`? Array iterated linearly?
   Trie keyed by slug? hand-rolled per host).
2. Lookup verbs (`get` / `find` / `findByType` / `findByOwner`
   diverge across hosts; consumers can't switch hosts without rewiring).
3. Capability indexing (every host hard-codes its own `if (provider ===
   "s3" || provider === "gcs") { fuse-bridgeable }` decision tree).
4. Discovery hooks (workspace-local doctypes via `EXTENSION.md`,
   provider files in a directory, MCP-published catalogs — none
   standardized).

The cost compounds: a doctype family ships with `defineX`, multiple
hosts each rewrite the registry plumbing, the registry shape drifts
between hosts, capability metadata becomes load-bearing in some hosts
and absent in others, and discovery (the most valuable cross-host
property — "give me every storage backend the host knows about") is
ad-hoc.

`agentregistry/v1` factors the registry side out the same way `AIP-1`
factored doctype identity: one shape, one set of verbs, one capability
namespace, valid across every doctype family.

The companion observation: `defineX` already returns a
**`createDoctype`-built handle** ([AIP-56](/docs/aip-56)). The registry doesn't
need to know which doctype it's storing — it operates on the universal
handle shape (id, frozen body, optional capabilities) and yields the
handle back unchanged. One impl, every doctype family.

## Specification

A conforming registry is an in-memory catalog with the operations,
identity rules, capability metadata namespace, and discovery hooks
defined below. The `@agentproto/registry` reference implementation
satisfies all of them; alternative implementations (a host that
persists handles to disk or fetches them from an HTTP catalog) MUST
satisfy the same observable contract.

### Identity

A registry is parameterised by a doctype handle type `H`. Every entry
has a string id derived from one of (in priority order):

1. `handle.id` — present on standalone doctype manifests (per AIP-2).
2. `handle.provider` — present on STORAGE / SANDBOX handles (the
   provider value, e.g. `"local-daemon"`, `"s3"`).
3. `handle.slug` — present on EXTENSION handles (`"acme:deal"`).
4. A registry-level `keyBy: (handle: H) => string` selector when
   none of the above apply.

Registries MUST refuse `register(...)` calls whose handle's id is
already present — the second registration is an error, not a
silent overwrite. Hosts that need replacement MUST call `unregister(id)`
first.

### Operations

The minimum surface is four verbs. A reference signature in TypeScript:

```ts
interface Registry<H> {
  /** Add a handle. Throws if `keyBy(handle)` is already present. */
  register(handle: H): void

  /** Get the handle by id. Returns undefined if absent. */
  get(id: string): H | undefined

  /** Every handle currently registered, insertion-ordered. */
  list(): readonly H[]

  /** Every handle matching `predicate`. */
  lookup(predicate: (handle: H) => boolean): readonly H[]
}
```

Hosts MAY extend the surface with sugar (`has`, `count`, `unregister`,
`replace`, `entries`) but MUST NOT remove or rename the four core verbs.

### Capability metadata namespace

A handle MAY carry a `capabilities` field — a free-form
`Record<string, unknown>`. The registry treats it as opaque (no
validation, no normalisation) but indexes it lazily for `lookup`.

Capabilities are **declarative metadata**, not behaviour. A storage
handle whose `capabilities.bridgeable === true` is asserting that the
backing store can be FUSE-mounted into a sandbox; the registry doesn't
verify the claim. Hosts use capabilities for cross-handle queries
("every storage backend whose `capabilities.transport` is
`'fuse'`") that would otherwise become hard-coded switch statements.

Suggested namespacing convention (NOT mandated):

| Family | Capability key | Meaning |
|---|---|---|
| STORAGE | `bridgeable: boolean` | Can the bytes be mounted into a sandbox? |
| STORAGE | `transport: "symlink" \| "fuse" \| "mcp" \| "tunnel"` | How a sandbox sees the bytes (when `bridgeable`). |
| STORAGE / SANDBOX | `pairsWith: string[]` | Backend ids of the other family that compose cleanly. |
| STORAGE / SANDBOX | `serverReachable: boolean` | Can a remote host reach this backend (false for `local-ide`/`local-daemon` on loopback)? |

Hosts SHOULD agree on convention names within a family but the registry
itself only relies on the field being a JSON value.

### Discovery hooks

A registry is hand-populated by default — hosts call `register(handle)`
for each handle they want to expose. Two optional discovery hooks:

1. **Directory scan.** A registry MAY accept a directory path on
   construction. Every `<file>.<doctype>.ts` file in the directory is
   imported, its default export validated as a handle of type `H`, and
   registered. The host sets the file naming convention; the registry
   doesn't impose one.

2. **MCP listing.** A registry MAY publish a `list_<doctype>` tool to an
   MCP server (per AIP-5 conventions); the tool returns
   `{ id, label?, description?, capabilities? }` per entry. This lets
   agents and external tooling enumerate the catalog without import access.

Discovery is OPTIONAL. A registry that only supports `register()` is
fully conforming.

### Equality and lifetime

Handles registered into a registry are immutable. The registry MUST NOT
mutate the handle body; consumers MUST NOT mutate it after registration
(the `createDoctype` `Object.freeze` invariant from
[AIP-56](/docs/aip-56) makes this
runtime-enforced for compliant handles).

The registry's lifetime is the host process. Persistence across
restarts (e.g. registries hydrated from a config file at boot) is the
host's concern — the registry primitive itself is in-memory.

### Reference signature

```ts
import { createRegistry } from "@agentproto/registry"

const storageRegistry = createRegistry<StorageHandle>({
  family: "storage",
  keyBy: (handle) => handle.provider,
})

storageRegistry.register(localDaemonStorage)   // defineStorage(...) result
storageRegistry.register(s3Storage)
storageRegistry.list()                          // readonly StorageHandle[]
storageRegistry.get("local-daemon")             // StorageHandle | undefined
storageRegistry.lookup(h => h.capabilities?.bridgeable === true)
```

The `family` field is informational (used in error messages, MCP tool
names if discovery is enabled). `keyBy` is required when the handle
type doesn't expose a recognisable id field; `createDoctype`-built
handles default to the rules in [Identity](#identity).

### Saved selectors (added 2026-10-23)

> **Draft AIP-43 amendment** (2026-10-23). *Normative identifiers
> (field names, literals, tool names) are English and final.*

**Problem.** `lookup(predicate)` takes a function. A function cannot be
saved by a user, sent over MCP, referenced from a policy, or shown in a
picker. Hosts that needed a named, reusable selection ("every model priced
at zero", "these three models in this order", "every tool that writes to
the network") each invented a private format: the reference
implementation has one for models only, and the older code paths it
replaced each hard-coded their own predicate (an id suffix check, a
literal list). [AIP-38](/docs/aip-38) grants (`scope: "selector:<id>"`)
and [AIP-46](/docs/aip-46) session configs (`model: "selector:<id>"`) now
reference selectors by id, so the format needs one definition.

A **saved selector** is the declarative, serializable form of `lookup`:
a named, ordered selection over one registry family, stored by the host
as user data.

#### The `Selector` document

JSON Schema:
[`resources/aip-43/draft/Selector.schema.json`](https://github.com/agentproto/agentproto/blob/main/specs/resources/aip-43/draft/Selector.schema.json).

```ts
interface Selector {
  /** Unique on the host across all families: /^[a-z0-9][a-z0-9-]{0,62}$/ */
  id: string
  /** The registry family it selects from: "model", "tool", "skill", ... */
  family: string
  label?: string
  /** Handles matching ANY clause are selected. */
  include?: Clause[]
  /** Handles matching ANY clause are removed. Wins over include and ids. */
  exclude?: Clause[]
  /** Explicit pins, by exact id. A pin need not be registered (see below). */
  ids?: string[]
  /** Default "listed". */
  order?: "listed" | { by: string; direction?: "asc" | "desc" } | string
  /** A hint for consumers that use one member at a time. Default "priority". */
  rotation?: "priority" | "round-robin" | "least-recently-limited"
}

type Clause =
  | { id: string }                       // exact id, or a `*`-suffix glob
  | { tag: string }                      // member of capabilities.tags
  | { capability: string                 // dot path into capabilities
      eq?: unknown; in?: unknown[]; lte?: number; gte?: number; exists?: boolean }
  | { selector: string }                 // composition: members of another selector
  | { all: Clause[] }                    // conjunction
```

- A `capability` clause with several comparators requires all of them. A
  missing capability matches only `exists: false`.
- `id` globs follow [AIP-38](/docs/aip-38) §Scope matching: `*` is a
  wildcard only as a suffix.
- A `selector` clause MUST name a selector of the same family. A cycle, an
  unknown selector, or a family mismatch is an error at **save** time, and
  at resolution time if the referenced selector was later deleted.
- A family MAY register named shorthand clauses that expand to the forms
  above (for example a model family `{ price: { maxInPer1M: 0 } }` expanding
  to a `capability` clause). Shorthands are sugar: the expansion is what is
  stored and evaluated, and `explain` (below) reports it.

#### Identity and membership

Resolution and membership compare ids through the family's **identity
normalization**: a family MAY declare, for an id, the set of equivalent
spellings (aliases, a route suffix such as `@openrouter` stripped, a
canonical id). Two ids are the same member when their normalized sets
intersect. This is load-bearing for `exclude`: a model excluded by its
canonical id stays excluded when addressed through an alias or a route
suffix.

- A pin in `ids` is a member even when no registered handle carries that
  id (a model the catalog does not know yet). Clauses cannot match an
  unregistered id, so only an `{ id }` clause in `exclude` removes such a
  pin.
- Membership (`has(selectorId, id)`) MUST be answerable without expanding
  the whole selector when the id is registered, and MUST give the same
  answer as expansion.

#### Resolution and order

`resolve(selectorId)` returns an ordered, de-duplicated list of ids:

1. include clauses in their declared order, each contributing matching
   handles in registry insertion order; then `ids` pins in their declared
   order; the first occurrence of a member keeps its position;
2. exclude clauses remove members;
3. `order` re-sorts: `"listed"` keeps step 1's order; `{ by, direction }`
   sorts on a capability path (default ascending; members missing the
   capability sort last, ties keep step 1's order); a string names an order
   the family declares (the model family declares `cheapest`,
   `largest-context`, `newest`).

Resolution is re-evaluated on every use: a registry refresh or an edit to
the selector (or to one it composes) takes effect at the next resolution.
A consumer that caches a resolution MUST invalidate it on either.

`explain(selectorId)` returns, for each member, the clause or pin that
included it, after shorthand expansion.

`rotation` does not change resolution. It tells a consumer that uses one
member at a time (an [AIP-46](/docs/aip-46) session failing over within a
selector) how to pick the next one: `priority` takes the next member in
order; `round-robin` continues after the member used last; and
`least-recently-limited` prefers the member whose most recent rate or quota
limit is oldest, members never limited first.

#### Storage, seeds and surface

Selectors are host configuration owned by the user, stored outside any
workspace or repository. The registry primitive stays in-memory; the
selector store is the host's.

- A host MAY ship **seed selectors** (for example `zero-cost`: the model
  family's members whose input and output prices are both 0). A seed is
  ordinary data: the user can edit it, the host MUST NOT re-impose its
  default over a user edit, and a host MAY refuse to delete a seed.
- Deleting a selector that a policy grant, a session config, a session
  preset or another selector references MUST be refused unless forced. A
  dangling reference resolves to an error, and every consumer treats that
  as described by its own AIP ([AIP-38](/docs/aip-38): fail closed).
- Surface (MCP, with HTTP and CLI mirrors):

| verb | input | output |
|---|---|---|
| `selector_save` | a `Selector` | the stored selector; refuses a cycle, an unknown or cross-family `selector` clause, an invalid id |
| `selector_list` | optional `family` | selectors |
| `selector_delete` | `id`, `force?` | refused while referenced, unless `force` |
| `selector_resolve` | `id` | `explain(id)`: members in order, each with the clause or pin that included it |

A host MAY expose family-scoped aliases of these verbs (for example
`model_list_save` for `family: "model"`); they MUST behave as the generic
verb with the family fixed.

#### Model family conventions

The model family is the registry consumers reference most (AIP-38
`model:invoke` scopes, AIP-46 `model`). Its handles SHOULD carry these
capabilities so selectors stay portable across hosts:

| capability | meaning |
|---|---|
| `provider` | the model builder |
| `kind` | `llm`, `embedding`, `image`, ... |
| `contextWindow` | input context size in tokens |
| `pricing.inputPer1M`, `pricing.outputPer1M` | public list price in USD |
| `variant` | route-identity variant (for example `free`) |
| `addedAt` | ISO-8601 date the model entered the catalog |
| `tags` | includes `price:zero` when both list prices are 0 |

Price is catalog data like any other capability. A selector such as
`zero-cost` is how a user names "free models"; no host rule is keyed on it.

## Why not just use a Map?

Three reasons:

1. **Identity selection is doctype-aware.** STORAGE keys on
   `provider`; EXTENSION keys on `slug`; a handle that's a standalone
   doctype keys on `id`. The registry's `keyBy` defaults pick the
   right one without the host wiring it case-by-case.

2. **Duplicate registration is an error, not silent overwrite.** A
   bare `Map.set` lets a second `defineStorage({ provider: "s3" })`
   silently replace the first; the registry refuses, surfacing the
   collision at boot.

3. **Capability lookup is the most useful operation.** `Map` exposes
   `get(key)` cheaply; `lookup(predicate)` is what hosts actually need
   ("every storage that pairs with sandbox X"). Standardising the verb
   keeps capability metadata normative across hosts.

## Backward compatibility

This AIP introduces no breaking changes. Existing hand-rolled host
registries remain functional — adopting `@agentproto/registry` is a
voluntary refactor. Handles produced by `defineStorage` / `defineSandbox`
/ `defineExtension` / `defineOperator` are already in the shape the
registry expects (the universal `createDoctype` handle), so adoption
is one `register(handle)` call per existing handle.

### The 2026-10-23 saved-selectors amendment (draft)

§Saved selectors is additive. `register`, `get`, `list` and `lookup` are
unchanged, and a host with no selector store is fully conforming for every
consumer that does not reference `selector:<id>`. A consumer that does
reference one (an AIP-38 scope, an AIP-46 `model`) on a host without
selectors gets a resolution error, which AIP-38 treats as a deny.

The reference implementation's model lists (`ModelList`, `model_list_*`
tools, `~/.agentproto/model-lists.json`) are saved selectors of
`family: "model"`. Their selector kinds map to clauses: `model` to `id`,
`tag` to `tag`, `provider` / `priceTier` / `kind` / `variant` to
`capability` with `eq`, `price` to `capability` with `lte` on
`pricing.*`, `context` to `capability` with `gte` on `contextWindow`, and
`list` to `selector`. `order` and `rotation` keep their values.

## Reference implementation

The canonical implementation is
[`@agentproto/registry`](https://github.com/agentproto/ts/tree/main/packages/registry).
It implements:

- `createRegistry<H>(options)` returning the four-verb surface plus
  `has`, `count`, `unregister`, `replace`, `entries` sugar.
- Default `keyBy` resolution per [Identity](#identity).
- Optional directory-scan discovery hook (Node-only; uses dynamic
  `import()` so it's tree-shakable).
- Optional MCP-tool discovery hook (depends on `@modelcontextprotocol/sdk`;
  feature-gated so non-MCP hosts don't pull the SDK).

Tests cover: identity selection priority, duplicate-registration
refusal, capability-lookup correctness, discovery-hook idempotency.
